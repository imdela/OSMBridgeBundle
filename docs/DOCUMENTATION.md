# OSMBridgeBundle Integration Guide

This guide describes the architecture and configuration required to successfully integrate **OpenSign** with **MinIO** for self-hosted digital signatures within a Symfony/Docker environment.

---

## 🏗️ Architecture Overview

The system consists of three main roles communicating in a local network:

1.  **Symfony App**: The business logic orchestrator. It generates PDFs, uploads them to OpenSign, and initiates signature requests.
2.  **OpenSign Server**: An open-source digital signature platform based on Node.js and **Parse Server**. It manages documents, signers, and the legal audit trail.
3.  **MinIO**: A high-performance, S3-compatible object storage server. It stores the physical PDF files generated by the app and used by OpenSign.

### 🔄 Communication Flow & Protocols

The interaction between these services uses standard HTTP/REST and S3 protocols:

| Source           | Destination      | Protocol    | Description                                                                    |
| :--------------- | :--------------- | :---------- | :----------------------------------------------------------------------------- |
| **Symfony**      | **OpenSign API** | REST (HTTP) | Symfony calls the Parse REST API to upload files and create document records.  |
| **OpenSign**     | **MinIO**        | S3 (Binary) | OpenSign stores and retrieves physical PDFs using the S3 protocol.             |
| **User Browser** | **MinIO**        | S3 (Binary) | Signers download the document via a pre-signed URL pointing directly to MinIO. |
| **User Browser** | **OpenSign UI**  | Web (HTTPS) | The signature interface is served by OpenSign and interacts with the API.      |

## 📦 Requirements & Platforms

### 1. OpenSign

- **Role**: Management of "contracts" and "signatures".
- **Version**: `2.37.0` (main container).
- **Database**: Needs a MongoDB instance to store its metadata.
- **Critical Fix**: Standard OpenSign expects AWS S3. For MinIO, it requires a "Path-Style" access patch.

### 2. MinIO

- **Role**: File storage.
- **Compatibility**: S3 API.
- **Networking**: Must be reachable by both OpenSign (for uploading) and the Application (for providing tokens).

## ⚙️ Configuration (Docker Compose)

The integration requires specific networking and volume mounts.

### The DNS Trick (Virtual Hosting)

OpenSign's S3 client often tries to access buckets via `http://bucketname.minio:9000`. We must alias our MinIO container to support this.

```yaml
ossmb-minio:
  image: quay.io/minio/minio
  networks:
    my-network:
      aliases:
        - minio
        - myapp.minio # <--- CRITICAL for OpenSign virtual hosting
```

### The S3 Adapter Patch

OpenSign 2.x defaults to "Virtual-Hosted" style URLs which fail on most local MinIO setups. We patch `index.js` to force Path-Style access:

**File: `resources/scripts/opensign-minio-patch.js` snippet:**

```javascript
// Add 'forcePathStyle: true' to the s3overrides object
s3overrides: {
    credentials: { ... },
    endpoint: spacesEndpoint,
    signatureVersion: 'v4',
    forcePathStyle: true, // <--- THE FIX
},
```

**Mount in `compose.yaml`:**

```yaml
opensign:
  volumes:
    - ./resources/scripts/opensign-minio-patch.js:/usr/src/app/index.js
```

## 🔑 Environment Variables (.env.dist)

In this project, `.env.dist` is used as the `env_file` in `compose.yaml`. This is the source of truth for the Docker environment.

| Key                      | Description        | Usage                                                    |
| :----------------------- | :----------------- | :------------------------------------------------------- |
| `OPENSIGN_APP_ID`        | App Identifier     | Header `X-Parse-Application-Id`                          |
| `OPENSIGN_MASTER_KEY`    | Administrative Key | Only for bootstrapping and schema management             |
| `OPENSIGN_API_URL`       | API Endpoint       | e.g., `http://opensign:3000/app`                         |
| `OPENSIGN_USER_ID`       | System User ID     | Generated during bootstrap, used as "Owner" of documents |
| `OPENSIGN_SESSION_TOKEN` | Auth Token         | Used for daily document creation calls                   |

> [!IMPORTANT]
> Since Docker only loads `env_file` on container startup, you must run `task restart` (or `docker compose up -d`) after the first setup to inject these keys into the running PHP container.

## 🚀 Automated Setup

We have automated the complex process of creating a user, generating a token, and initializing the MongoDB schema.

### 1. The Symfony Command

Run this command inside the PHP container to bootstrap the entire environment. It will update `.env.dist` and `.env.test`.

```bash
# Inside the container
bin/console ossmb:opensign:setup .env.dist
bin/console ossmb:opensign:setup .env.test
```

### 2. The Taskfile shortcut

If using `Task`, simply run:

```bash
task opensign:setup
```

**What this does:**

1.  Creates a user `api-system@myapp.com`.
2.  Logs in to retrieve a permanent `sessionToken`.
3.  Initializes the `contracts_Document` collection schema in MongoDB.
4.  Safely writes the credentials into `.env.dist` and `.env.test` using `DotEnvEditor`.
5.  **Requires a Restart**: Reminds you to restart the environment so Docker picks up the new `.env.dist` values.

### 3. Resetting the Environment

If your OpenSign configuration becomes corrupted or you want to start from a clean slate:

```bash
task opensign:reset
```

This will:

1.  **Drop** the `opensign` database in MongoDB.
2.  **Re-run** the user creation and schema initialization.
3.  **Update** your tokens in `.env.dist` and `.env.test`.

## 💻 Symfony Implementation Example

### 1. OpenSignService

The service should handle two main tasks:

- `uploadFile()`: Uses standard `multipart/form-data` to send the PDF.
- `createSignatureRequest()`: Uses a `sessionToken` to create a record in `contracts_Document`.

### 2. The Payload

The payload sent to OpenSign must match their internal naming convention:

```php
$payload = [
    'Name' => 'Contract Oct 2024',
    'URL' => $uploadResult['url'],
    'Signers' => [['name' => 'John Doe', 'email' => 'john@client.com']],
    'Placeholders' => [['name' => 'John Doe', 'email' => 'john@client.com']],
    'Status' => 'completed'
];
```

## 🛑 Troubleshooting

- **Code 130 (UnknownError)**: Check if `forcePathStyle` is actually applied in the container's `index.js`.
- **Code 119 (Permission Denied)**: Ensure you are using a `X-Parse-Session-Token` and that the user has write access to the `contracts_Document` class.
- **Bad Request (JSON undefined)**: Ensure you are sending `Signers` as an **Array of Objects**, not just strings.
